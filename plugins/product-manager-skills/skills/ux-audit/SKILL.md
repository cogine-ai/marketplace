# 产品 UX 巡检

按用户指定的设计原则走查现有产品。默认原则：**通过布局、分组、控件、状态和反馈，让用户靠直觉理解界面，减少解释性文案。**

说明文案只是线索，须指出结构或交互为何迫使用户读规则、猜用途。优先改结构和交互；保留必要标签、数据、单位、状态、错误与操作后果，避免换成陌生图标或隐藏提示。

## 走查

1. 读取项目约定和设计系统，确认目标用户、核心任务，列出主要模块、入口和相关状态。先覆盖主要模块，再深入首次使用与高频流程，不能只审首页。
2. 优先重走实际界面并截图，用源码解释根因。无法访问时，根据已有截图、源码或资料继续，注明证据类型；按已有证据限定结论，不把缺失资料当作缺失功能。
3. 检查用户能否直接看懂当前位置、操作对象、下一步、控件关系、当前状态和操作结果；对其他指定原则采用相应判断。
4. 复核并按原则违背程度与任务影响筛出 3–5 处，合并同一根因。不按修复容易程度排序；可信问题不足时照实输出，不凑数。

## 图证

每项展示现状截图；无法截图时，提供有来源的结构示意，注明“基于……，未实机验证”。未知组件和样式不补画成事实；没有足够依据的项列为待确认候选。

- **保持比较一致：** 界面内文案沿用产品语言，报告和外部批注使用用户语言。建议图沿用已知字体与设计系统；未知时用统一中性线框，注明样式未核实。涉及字体、排版或本地化的结论，使用真实界面或已核实样式的渲染证据。
- **让图可读：** 渲染后检查字体可显示、文字不裁切、不异常断词、标注不遮挡。长分析留在报告，图中只保留必要界面内容和短批注。
- **区分现状与建议：** 改法适合时配目标示意，单独标注；建议图不能充当现状证据。报告内嵌可查看的图，并链接文件，不能只列路径或写“待补截图”。

## 交付

开头简述原则、走查范围和影响结论的缺口，区分实机观察、用户截图、源码推断与未覆盖部分。按优先级展示发现，每项包含：

- **位置、状态与任务**，有源码时附组件/文件定位。
- **现状图与问题**：哪里难以理解或操作，为什么违反原则；区分事实与推断。
- **具体改法**：调整哪个结构、控件或反馈，哪些解释可去掉、必要信息应保留。
- **验收任务**：重走什么操作、应观察到什么结果；建议验收与已执行检查分开。

仅要求巡检时交付报告和图。用户同时授权修复时，实施后重走相关流程，提供同等状态的前后证据并注明验证结果。
